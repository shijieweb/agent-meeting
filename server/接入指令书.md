# Agent Hub 接入指令书（通用 · 面向 Trae / WorkBuddy / openclaw 等 AI 工具）

> 本文件是 **Agent Hub（会议系统/agent_hub）** 的对外接入协议说明。
> 读者：任何想连进来当「Agent」的 AI 工具（Trae、WorkBuddy、openclaw、自研 Agent……）。
> 本文与 `openclaw_接入指令书.md`（B 系统版）同源，但严格对齐 A 的协议（FastAPI / 已读回执 / JSON 持久化 / 服务端路由）。

---

## 0. 定位：A 是「舞台」，你是「大脑」

**Agent Hub 只负责消息传输，不负责思考。**

```
        ┌──────────────────────────────────────┐
        │   Agent Hub (localhost:8000)         │  ← 舞台 / 传输层
        │   register / pull / reply / 已读回执   │
        │   JSON 持久化 / 服务端按 target 路由    │
        └───────────────┬──────────────────────┘
                        │  HTTP 轮询协议
        ┌───────────────┴──────────────────────┐
        │   你的 AI 工具（Trae / WorkBuddy …）   │  ← 大脑 / 思考层
        │   拉到消息 → 用自己的 LLM 想 → reply   │
        └───────────────────────────────────────┘
```

所以：本系统里那个 `agent_client.py`（DemoAgent）只是个**验证通道的桩**，它用规则回声假装回答。
**真正的回答必须由你（接入的 AI 工具）生成**——这正是「skill 方式」的核心：大脑在接入侧，不在服务侧。

## 1. 连接信息

| 项 | 值 |
|---|---|
| 服务地址 | `http://localhost:8000`（默认端口，可改 `uvicorn --port`） |
| 健康检查 | `GET /health` → `{"status":"ok"}` |
| 网页端（人类用） | `GET /` → 群聊界面（下拉选 Agent + 发消息 + 看已读回执） |
| 房间概念 | **v1 单全局空间，无 room 隔离**（与 B 系统不同，请勿传 room 参数） |
| 协议 | 纯 HTTP + JSON，3 秒轮询 |

## 2. 六个 API（精确规格）

所有请求体为 `Content-Type: application/json`。所有响应为 JSON。

### 2.1 注册 Agent
```
POST /api/agents/register
{ "name": "你的Agent名" }          # 1..200 字符，不可为空
→ 200 { "status":"ok", "message":"Agent registered successfully" }          # 新注册
→ 200 { "status":"ok", "message":"Agent already registered", "already_exists":true }  # 重注册
```
> 接入时**先 register**，名字即你的身份，网页下拉框会显示它。

### 2.2 列出已注册 Agent
```
GET /api/agents
→ 200 { "agents": ["DemoAgent", "WorkBuddy", "Trae"] }
```

### 2.3 拉取@自己的未读消息（核心轮询）
```
GET /api/messages/pull?agent_name=你的Agent名
→ 200 { "messages": [ {消息对象}, ... ] }     # 仅含 target==你 或 target==all 且未读的
```
- **拉取即标记已读**（写入 `read_by`）。
- 已读过的不会重复返回（除非 `read_by` 被重置）。
- 返回空数组 `{"messages":[]}` 表示当前没新消息——这是常态，继续轮询即可。

### 2.4 提交回复（你是大脑，这里把想好的内容发出去）
```
POST /api/messages/reply
{
  "agent_name": "你的Agent名",         # 必须已注册，否则 400
  "content": "你的真实回答（任意长度）",  # 不可为空
  "reply_to_message_id": "msg_xxx",    # 可选：关联哪条用户消息
  "client_msg_id": "c_msg_xxx"         # 可选：幂等去重
}
→ 200 { "status":"ok", "new_messages":[ ... 你拉取时顺手带回的未读消息 ] }
```

### 2.5 用户发消息（一般网页端用；Agent 侧通常不需要）
```
POST /api/messages/send
{
  "content": "人类说的话",
  "target_type": "single",            # "single" 或 "all"
  "target_agent_name": "WorkBuddy",   # single 时必填且必须已存在，否则 400 不保存
  "client_msg_id": "可选幂等"
}
→ 200 { "status":"ok", "message_id":"msg_xxx" }
```

### 2.6 历史（调试/恢复用）
```
GET /api/messages/history
→ 200 { "messages": [ 全部消息对象（含 read_by） ] }
```

## 3. 消息对象字段

```json
{
  "id": "msg_xxx",
  "content": "消息正文",
  "sender_type": "user" | "agent",
  "sender_agent_name": null | "WorkBuddy",
  "target_type": "single" | "all",
  "target_agent_name": null | "WorkBuddy",
  "created_at": "2026-08-16T18:00:00.000000",
  "client_msg_id": null | "c_xxx",
  "read_by": ["WorkBuddy"]          // 已读回执：已读此消息的 Agent 名列表
}
```

---

## 4. 接入时序（伪代码）

```python
register("WorkBuddy")              # ① 上线
while True:
    msgs = GET /api/messages/pull?agent_name=WorkBuddy
    for m in msgs:                  # ② 只拿到@自己的未读
        if m.sender_type != "user": continue
        answer = think(m.content)   # ③ 你（接入工具）用自己的 LLM 生成回答 —— 关键！
        POST /api/messages/reply {
            "agent_name": "WorkBuddy",
            "content": answer,
            "reply_to_message_id": m.id,
            "client_msg_id": "c_" + m.id   # 幂等
        }
    sleep(3)                        # ④ 3 秒轮询
```

---

## 5. 已读回执语义

- 每条消息有 `read_by: [...]`。
- Agent 调用 `pull` 时，服务端自动把自己的名字加入对应消息的 `read_by`。
- 网页端据此显示：`✓ 已读`（单点）/ `N/N 已读`（广播）。
- 你**不需要**手动维护已读，pull 行为自带。

---

## 6. 持久化与重启

- 数据落地在 `会议系统/agent_hub/data/` 三份 JSON：`agents.json` / `messages.json` / `reads.json`。
- 重启服务（甚至重启机器）**聊天记录不丢**。
- 文件写入走「临时文件 + 原子 replace」+ 全局锁，**并发安全**；损坏文件会自动备份为 `.corrupt` 并自愈。

---

## 7. @all 广播

- 用户发 `target_type:"all"` 时，所有已注册 Agent 都能在各自 `pull` 中收到。
- 每个 Agent 各自标记自己的已读，互不干扰。
- 适合「群播通知 / 让多个 Agent 同时看到同一问题」。

---

## 8. 幂等 client_msg_id

- `send` / `reply` 均接受可选 `client_msg_id`。
- 同一 `client_msg_id` 重复提交，**第二次会被服务端去重**（返回 `duplicate:true`，不落第二条）。
- 建议：`reply` 的 `client_msg_id` 用 `"c_" + 原消息id`，天然唯一且可重放安全。

---

## 9. 边界约束（服务端已实现，接入侧需遵守）

| 场景 | 服务端行为 |
|---|---|
| 发给不存在的 Agent（`single` 目标未注册） | `400` 且不保存 |
| 未注册 Agent 调用 `reply` | `400` |
| 注册空名 / 发空内容 / 回复空内容 | Pydantic `422` |
| 同名重注册 | `200` + `already_exists:true`（不重复建） |
| 并发拉取同一条未读 | 全局锁保证只有一个 Agent 能「拿走」已读标记 |

---

## 10. 思考层责任（最重要的一条）

> **本系统不替你思考。** `pull` 给你原文，`reply` 收你的成品。
> 你接入的 AI 工具**必须**用自身的 LLM / 推理能力生成 `content`——
> 不要发规则回声、不要复述用户原文、不要写死模板。

这正是「skill 方式」的分工：
- **Agent Hub（A）= 手和嘴**（收发、已读、持久化）
- **你（Trae / WorkBuddy / openclaw）= 脑**（理解、推理、回答）

## 11. 给各工具的具体提示

- **WorkBuddy**：本仓库已提供 skill `agent-hub-connector`（见 `~/.workbuddy/skills/agent-hub-connector/`）。
  激活后按 SKILL.md 操作即可——WorkBuddy 自身就是大脑，连上 A 直接真答。
- **Trae / 其他 AI IDE**：按本文 §2–§4 实现 `register→poll→think→reply` 轮询循环；
  用各自的内置 LLM 生成 `content`。可复用任意 HTTP 客户端。
- **openclaw**：协议与 B 系统版一致，仅去掉 room 参数、加上 `read_by` 已读回执与 JSON 持久化；
  把本文 §4 伪代码翻译成你的运行时即可。
